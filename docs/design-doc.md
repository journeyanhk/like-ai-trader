# AI 交易智能体搭建提示词 - 评估、修订版与落地步骤

## TL;DR

截图这份提示词的**骨架是对的**——"研究模型提假设、确定性代码管风控和执行"、"先模拟后实盘"、"防未来数据泄露"这三条是 AI 交易系统最容易踩坑的地方，它都点到了。但它有四个硬伤：**没定市场/交易所/技术栈、没定义 LLM 到底在哪一环出手、没有可量化的验收门槛、没有订单幂等与断线对账细节**。直接拿去给模型，大概率得到一个"看起来完整但跑不起来、也不敢跑"的半成品。

另外要先说清楚一个预期："**一个文件、10 分钟构建**"只能产出一个可以做模拟交易的骨架，不可能产出一个敢接真钱的系统。下面给出修订后的完整提示词（可直接复制）以及从零到受控实盘的 9 步路线。

---

## 截图提示词评估

整体思路合格，但"宣传语级别"的描述太多，缺少让模型无法含糊的硬约束。逐项对照如下：

| 维度 | 截图现状 | 问题 | 修订方向 |
|---|---|---|---|
| 市场与标的 | "加密与美股分别处理" | 范围太宽，模型会同时写两套接口，两套都不深 | **只选一个**市场、一个交易所、一组标的起步 |
| 技术栈 | 未指定 | 模型自由发挥，可能混用框架 | 明确 Python 3.11 + ccxt + SQLite + APScheduler |
| LLM 的角色 | "研究模型提出假设" | 没说 LLM 是否参与实时下单；若参与，延迟、成本、不确定性全失控 | **LLM 只离线产策略/标注市场状态，永远不直接下单** |
| 策略定义 | "按市场状态选择策略" | 市场状态没有量化定义，等于没定义 | 用 ADX / ATR 百分位 / 均线斜率等可计算规则定义 regime |
| 回测成本 | "计入手续费、滑点、资金费率" | 没给数值，模型会用 0 或随意值 | 给出 maker/taker 费率、滑点 bps、资金费率来源 |
| 验收标准 | "模拟交易达标" | 没有数字，无法判断"达标" | 样本外 Sharpe、最大回撤、交易笔数、实盘/回测偏差阈值 |
| 执行细节 | "处理部分成交、撤单、重试" | 缺 clientOrderId 幂等、重启后对账、交易所限频 | 补订单状态机 + 启动即对账 |
| 熔断触发 | "紧急停机开关" | 只有手动开关，没有自动触发条件 | 数据过期 >N 秒、价差异常、API 错误率、日亏触发自动停 |
| 测试 | 只有"最终验收" | 没有单元测试和模拟交易所 | 要求 mock exchange + 回放测试 |
| 交付物 | "可运行系统与配置文件" | 没有文件清单 | 列出具体文件及职责 |

风控数值本身（单笔 0.5%、日亏 2%、回撤 10%）是合理的保守起点，可以保留。

## 修订版完整提示词

以下为可直接使用的版本。`【】`内是你需要填写的参数，填完再发给模型。核心变化：加入了硬性约束、LLM 边界、量化验收和交付清单。

```text
<角色>
你是一位资深量化交易系统工程师。你的任务是构建一个可持续运行的、以模拟交易为第一阶段的自动化交易系统。
原则：研究由模型提出假设，风控和执行由确定性代码完成。LLM 在任何情况下都不直接生成或发送订单。
</角色>

<硬性约束>
1. 市场：【加密货币永续合约 / 加密现货 / 美股】，只做这一个市场。
2. 交易所：【Binance / Bybit / Hyperliquid / Alpaca】，使用其官方测试网或纸面账户。
3. 标的：【BTC/USDT, ETH/USDT】，初期不超过 3 个。
4. 周期：主周期【1h】，确认周期【4h】。
5. 技术栈：Python 3.11，ccxt（行情与下单），pandas/numpy（计算），SQLite（存储），APScheduler（调度），python-telegram-bot（告警）。不引入其他框架。
6. 密钥只从环境变量读取（.env 文件，加入 .gitignore），任何日志、异常栈、数据库都不得出现密钥。
7. 所有时间统一为 UTC 毫秒时间戳；价格与数量精度从交易所 market info 读取，不硬编码。
8. 初始运行模式强制为 PAPER；切换到 LIVE 需同时满足配置文件 mode=live 和环境变量 ALLOW_LIVE=1。
</硬性约束>

<架构>
system/
  config.yaml          全部参数（标的、周期、风控、费率、运行模式）
  main.py              入口：调度循环、状态恢复、异常捕获
  data/feed.py         行情拉取（REST 轮询 + 可选 WebSocket），数据质量检查
  data/store.py        SQLite 读写：candles, signals, orders, fills, positions, equity, events
  research/regime.py   市场状态判定（确定性规则）
  research/strategy.py 策略接口 + 具体策略实现
  backtest/engine.py   事件驱动回测，含成本模型，禁止未来数据
  backtest/walkforward.py 滚动样本外验证
  risk/engine.py       仓位计算、敞口上限、熔断
  exec/broker.py       订单状态机、幂等、重试、对账
  exec/paper.py        模拟成交引擎（按下一根 K 线开盘价 + 滑点成交）
  monitor/alerts.py    Telegram 推送
  monitor/dashboard.py 终端或简单 HTML 面板
  tests/               单元测试 + mock 交易所 + 历史回放测试
</架构>

<LLM 边界>
- LLM 只用于：离线提出策略假设、解释信号逻辑、撰写每日复盘文字。
- LLM 不用于：实时判断方向、计算仓位、生成订单参数。
- 如需 LLM 标注市场状态，其输出只能作为"建议标签"写入数据库，不进入下单路径。
</LLM 边界>

<市场状态定义（确定性）>
- 趋势：ADX(14) > 25 且 EMA20 斜率同向
- 震荡：ADX(14) < 20
- 高波动：ATR(14)/收盘价 处于过去 90 天的 80 分位以上
- 低流动性：24h 成交量低于 30 日均值的 50%，或点差 > 配置阈值
每种状态对应允许运行的策略列表；状态不明确时不开新仓。
</市场状态定义>

<策略引擎>
每个策略必须实现：
- name, version
- entry(bar, context) -> Signal | None
- exit(bar, position, context) -> ExitSignal | None
- allowed_regimes: list
- invalidation: 失效条件的可计算描述（例如连续 20 笔交易 profit factor < 1.0 即自动下线）
初始提供两个基线策略：趋势跟随（EMA 交叉 + ATR 止损）和均值回归（布林带 + RSI），用于验证整个管线，不代表最终策略。
</策略引擎>

<回测与验证>
- 成本模型：taker 费率【0.05%】、maker 费率【0.02%】、滑点【5 bps】、资金费率按历史数据计入（永续）。
- 严格使用 bar 收盘后才可见的数据产生信号，下一根 bar 开盘成交。
- 滚动验证：训练窗口【180 天】，测试窗口【60 天】，步长【30 天】，至少覆盖一轮上涨、一轮下跌、一轮震荡。
- 报告指标：年化收益、Sharpe、Sortino、最大回撤、profit factor、胜率、交易笔数、平均持仓时间、样本内外差异。
- 参数敏感性：关键参数 ±20% 扰动后结果不应崩塌。
</回测与验证>

<风控（确定性，不可被策略覆盖）>
- 单笔风险：账户权益的 0.5%，仓位 = 风险金额 / (入场价 − 止损价)
- 单日亏损上限：2%，触发后当日停止开新仓
- 最大回撤阈值：10%，触发后全平并锁定，需人工解锁
- 总敞口上限：权益的【100%】；单标的上限【50%】；杠杆上限【3x】
- 相关资产合并计算敞口（BTC/ETH 视为同一组）
- 自动暂停条件：行情数据过期 > 60 秒；本地持仓与交易所持仓不一致；订单状态超过 30 秒未知；连续 API 错误 ≥ 5 次；两个价格源偏差 > 0.5%
- 以上参数从 config.yaml 读取，并在回测和模拟交易中验证后再调整
</风控>

<订单执行>
- 每个订单带唯一 clientOrderId（策略名 + 信号时间戳 + 标的），重试时复用，防止重复下单
- 订单状态机：PENDING -> SUBMITTED -> PARTIAL / FILLED / CANCELED / REJECTED / UNKNOWN
- 启动时先对账：拉取交易所持仓与未成交订单，与本地数据库比对，不一致则告警并进入只读模式
- 遵守交易所限频，所有调用带超时和指数退避
- 部分成交：剩余量按策略规则决定追单或撤单，不允许无限追
</订单执行>

<监控与告警>
- 每根 bar 结束后记录：权益、浮动盈亏、敞口、持仓、未成交订单、最近数据时间
- Telegram 推送：开平仓、风控触发、自动暂停、对账失败、进程重启
- 每日 UTC 00:00 生成复盘：当日交易、策略表现、异常事件、待验证改进点
- 心跳：每 5 分钟一次，连续 3 次缺失视为宕机
</监控与告警>

<测试要求>
- 单元测试：仓位计算、风控触发、订单状态转换、数据质量检查
- mock 交易所：模拟断线、限频、部分成交、重复响应、订单丢失
- 回放测试：用历史数据驱动整条管线，确认回测与模拟交易逻辑一致
</测试要求>

<交付物>
1. 完整代码及 config.yaml 示例
2. README：安装、配置、启动 paper 模式、切换 live 的步骤和前置条件
3. 回测报告模板与首次运行结果
4. 每日复盘模板
请按 架构 -> 数据层 -> 回测 -> 风控 -> 执行 -> 监控 -> 测试 的顺序分阶段输出，每阶段先说明设计再给代码，代码必须能直接运行。
</交付物>

<验收标准（全部满足后才允许讨论实盘）>
- 滚动样本外验证：Sharpe > 1.0，最大回撤 < 15%，交易笔数 > 100
- 模拟交易连续运行 ≥ 30 天，无未处理异常
- 模拟交易期间净值曲线与同期回测偏差 < 20%
- 所有自动暂停条件各触发至少一次并被正确处理
- 实盘首期资金不超过总资金的 5%
</验收标准>
```

## 一步一步搭建路线

建议把流程拆成 9 步，前 6 步是"让它跑起来"，后 3 步是"让它敢跑"。多数人失败不是因为代码写不出来，而是跳过了第 7-9 步。

| 步骤 | 做什么 | 关键产出 | 预计耗时 |
|---|---|---|---|
| 1. 定范围 | 选一个市场、一个交易所、1-3 个标的、一个周期；注册测试网 / 纸面账户，拿到 API key | 填好的 config.yaml | 1 小时 |
| 2. 搭环境 | Python 3.11 虚拟环境，安装 ccxt、pandas、apscheduler、python-telegram-bot；写 .env 并加入 .gitignore | 能连通测试网并拉到一根 K 线 | 1 小时 |
| 3. 数据层 | 拉取并存储历史 K 线（至少 1 年）、写数据质量检查（缺口、重复、时间戳乱序） | SQLite 中的 candles 表 | 半天 |
| 4. 回测 | 用修订提示词让模型生成事件驱动回测引擎，先跑两个基线策略，确认成本模型生效 | 首份回测报告 | 1 天 |
| 5. 滚动验证 | 跑 walk-forward，检查样本内外差异和参数敏感性；表现崩塌的策略直接丢弃 | 样本外报告 | 1 天 |
| 6. 风控 + 执行 | 实现风控引擎、订单状态机、模拟成交引擎；启动即对账 | PAPER 模式可全天候运行 | 1-2 天 |
| 7. 监控 | Telegram 告警、心跳、每日复盘脚本；用 systemd 或 Docker 保证进程重启 | 收到第一条告警 | 半天 |
| 8. 模拟验证 | 模拟交易连续跑 30 天；人为制造断网、杀进程、改错配置，确认每个自动暂停条件都触发过 | 验收清单打勾 | 30 天 |
| 9. 受控实盘 | 用 ≤5% 资金切 LIVE；前两周单笔风险减半；每天对账；任一验收指标失效立即回退 PAPER | 实盘日志 | 持续 |

几点实操提醒：

- **第 1 步最重要**。加密永续（如 Binance 测试网或 Hyperliquid）对新手最友好：24 小时交易、费率透明、ccxt 支持好；美股要处理交易日历、盘前盘后和 PDT 规则，先不要碰。
- **第 4 步给模型喂提示词时分阶段来**：一次让模型输出全部代码，质量会明显下降。按交付物里的顺序，一个模块一个模块地要。
- **第 8 步不要缩短**。30 天是为了至少经历一次周末低流动性、一次交易所维护、一次剧烈行情。

## 行情数据接入示例

你的"市场分析"模块需要的输入，大致就是下面这类数据。以 2026-10-08 09:20 UTC 的 BTC 为例：Binance BTC/USDT 现价 **$82,970**，24h **-0.97%**，区间 $82,228 - $83,936；永续资金费率 **-0.0016% / 8h**（年化约 -1.7%），未平仓合约 **$7.95B**；恐惧贪婪指数 **63（贪婪）**，已从 10 月 5 日的 74 连续回落。

按修订提示词里的状态定义，这类输入会被转化成几个确定性标签：价格在 24h 区间中段、资金费率略负说明多头拥挤度不高、情绪指数从高位回落——合起来更像"趋势减弱 / 偏震荡"的状态，这时趋势策略应被 regime 过滤掉，只允许均值回归类策略开仓。这正是"按市场状态选择策略"应该落地的方式：**用可计算的规则，而不是让模型凭感觉判断**。

研究层的数据源可以组合使用交易所 API（K 线、深度、资金费率、持仓量）、情绪指标、清算数据和新闻流；执行层只用交易所自己的数据，避免多源不一致导致的误下单。

## 风险与常见失败点

即便架构正确，这类系统最常在以下几处翻车，提示词里已针对性加了约束，但你在验收时要重点核查：

| 失败点 | 表现 | 提示词中的对应约束 |
|---|---|---|
| 未来数据泄露 | 回测年化 200%，实盘亏损 | bar 收盘后出信号、下一根开盘成交 |
| 重复下单 | 断线重连后多开一倍仓位 | clientOrderId 幂等 + 启动对账 |
| 过拟合 | 样本内漂亮、样本外崩塌 | 滚动验证 + 参数 ±20% 扰动 |
| LLM 介入执行 | 同一输入两次输出不同方向、延迟数秒 | LLM 边界章节，不进下单路径 |
| 无自动熔断 | 数据停更后仍按旧价下单 | 数据过期 >60s、价差 >0.5% 自动暂停 |
| 幸存者偏差 | 只回测了当前还活着的标的 | 初期固定 BTC/ETH 等主流标的可规避 |

另一个要正视的事实：**稳定盈利的策略不是提示词能给你的**。这套系统能保证的是"不会因为工程失误亏钱"，策略本身是否有优势，只能靠第 5 步和第 8 步的数据说话。

## 结论

截图提示词的设计哲学正确，但停留在"原则层"，缺少让模型无处含糊的硬约束。修订版补上了四件事：锁定单一市场与技术栈、划清 LLM 不碰执行的边界、把市场状态和风控写成可计算规则、把验收变成可勾选的数字。"10 分钟一个文件"可以用来生成第 2-4 步的骨架，但从骨架到敢投 5% 资金，按上面的路线走至少需要 **5-6 周**，其中 30 天是不能压缩的模拟运行期。

**底线。** 先用修订版提示词在测试网跑通 PAPER 模式，30 天后对照验收标准逐项打勾；任何一项不满足就不要切 LIVE——这套系统的价值首先是"不犯工程错误"，其次才是赚钱。
